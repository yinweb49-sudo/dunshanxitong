# 第 3、4 道盾：登录、会话、注册、找回与验证码

11-01 攻击里，登录和注册类接口吃掉了 97% 的请求：代理后台登录 14.3 万次、找回密码 9.4 万次（两天合计）、会员注册 1.6 万次、员工注册 8488 次。这一层守住了，攻击就拿不到结果。

## 1. 登录

**必须**

1. 失败提示只有一句："用户名或密码错误"。用户不存在时也做一次假的密码哈希比对，让耗时一致。
2. 风控两层（阈值见 `ip-ratelimit-blocking.md` §2.1）：
   - 账号×来源：失败若干次后要图形验证码，再多就冷却几分钟，到点自动解除，不需要管理员介入。
   - 来源级：同一来源不分账号的失败总数，超了整个来源暂停。
   - 冷却期内即使密码正确也不放行，所以"是否冷却"要在校验密码之前判断。
3. **所有能签发登录态的入口共用一个"能不能登录"判断**：账号密码、扫码登录、OAuth 静默授权、客户端签名跳转、刷新当前用户（`/me`）。停用账号、被识别为攻击号的账号在这里统一拦。案例：攻击号特征出来后，一次替换了 12 处"是否已停用"的判断。
4. 每个后台都按后台标准防：员工后台、代理 / 合作方后台、服务商后台。案例：代理后台登录被爆破 14.3 万次，当时它还没接入会员登录风控。
5. **防撞库**：撞库工具（如 OpenBullet2）配代理池，多 IP、低频，每个账号只试一两次，按 IP 限速抓不住。要按账号统计跨 IP 的失败次数，超过阈值后对这个账号要求图形验证码（不直接锁号，否则外人可以恶意锁人）；后台账号再叠加陌生设备验证。
6. 改密码、改手机号、改收款信息、绑定 / 解绑微信之前，要求重新输入密码或短信验证。
7. 可选：注册和改密时拦截已泄露的密码（Have I Been Pwned 的泄露密码库可以离线下载、按哈希前缀查询）。

**后台额外：陌生设备二次验证**（参考项目员工后台已上线，打扰度为 0）

- 只认一个风险信号：这台设备验证过没有。不用 IP、地理位置、登录时段拦截（员工常在家或异地办公，误判多、打扰多），这些只记录。
- 密码正确 + 设备陌生 → 不签发会话，发一张验证票据（10 分钟、绑定该员工、完成登录时一次性消费）。
- 验证顺序：扫已绑定的微信 → 未绑定的走在册手机号短信，通过后自动绑定这个微信 → 扫码连续失败 2 次或微信服务不可用时自动转短信。界面上不并列摆两个选项。
- 通过后种设备凭证 Cookie：32 字节随机数，`HttpOnly + Secure + SameSite=Lax`，服务端只存 SHA-256，90 天有效。**设备凭证只表示"这台设备验证过"，不等于已登录**，必须密码正确 + 设备匹配才签发会话。
- 员工已有绑定微信时，用别的微信扫码一律拒绝，不静默换绑（换绑等于账号接管路径）。换微信由管理员代解绑。
- 员工能看自己的登录记录和已记住的设备，能"不再信任"某台设备；超管能看失败排行、被限速次数、验证通过率。
- 票据、轮询令牌走 POST 请求体，不进 URL（会进访问日志）；服务端存哈希。

**后台额外：防盗 Cookie 和代理钓鱼**

2025～2026 年后台失守最常见的方式已经不是爆破，而是两种：员工电脑中了窃密木马，浏览器里的会话 Cookie 被整包偷走；或者员工点进一个实时转发的钓鱼页，对方把密码、短信、扫码验证都代为转发，最后拿到登录后的会话。陌生设备验证挡不住这两种——设备凭证 Cookie 会被一起偷走或转发。

1. **高危操作当场重新验证**（正常档起）：导出、退款、改权限、查看凭证明文时，要求重新输入密码或扫码，不只认已有会话。偷来的会话做不了最值钱的事。
2. **通行密钥**（极度档）：超管、财务等高权限账号用通行密钥（Passkey / WebAuthn）登录。通行密钥绑定真实域名，钓鱼页拿不到。ASP.NET Core 10 Identity 自带通行密钥支持；不用 Identity 的可用 fido2-net-lib。
3. **会话突变只告警**（极度档）：同一会话中途 IP 归属地或运营商变了，推一条告警给本人和超管，不拦截（守打扰度原则，员工本来就常换网络）。
4. 员工电脑：客服、财务这些能进后台的电脑，和开发机一样要有杀毒、不装来路不明的软件和破解工具；后台密码不存在浏览器里。

## 2. 会话

1. Cookie：`HttpOnly`；`Secure`（生产强制，ASP.NET Core 设 `Cookie.SecurePolicy = Always`）；`SameSite=Lax`（后台可用 Strict）；不同端用不同 Cookie 名和不同认证方案。时长按端区分：员工后台 8 小时滑动、合作方后台 12 小时、会员 30 天。
2. 服务端能让旧会话立即失效：账号上存一个版本号，改密码、重置密码、禁用、强制下线时加 1；每个请求比对 Cookie 里的版本号（带 60 秒短缓存）。
3. 每个请求校验账号当前状态（禁用、审批中、合作方被停用），不能只在登录时查一次。
4. 接口未登录返回 401、无权限返回 403，不做 302 跳登录页。
5. 会话加密密钥（ASP.NET Core Data Protection、Express session secret 等）持久化到发布目录之外的固定位置，固定应用名。否则每次发版重启全员被踢，还可能被人为制造"踢人"。
6. 登录态不放 `localStorage`。桌面客户端的 token 放在主进程，渲染层拿不到。
7. 敏感 token 尽量不进 URL。不得不进的（旧客户端签名跳转），响应加 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`、`X-Robots-Tag: noindex`，并且用完立刻换成 Cookie 再跳转。
8. CSRF：Cookie 认证 + `SameSite=Lax` 能挡住大部分跨站提交；修改类操作不用 GET；JSON 接口只收 `application/json`（框架默认对其他类型回 415）；跨子域调用只放行白名单来源，不配 `*` 加凭证。
9. 会话 Cookie 名用 `__Host-` 前缀（浏览器强制要求 Secure、Path=/、不能带 Domain，子域写不进来）；改名会让现有用户全部重新登录，新项目开工时就定好。
10. 登录、提权、改密后重新签发会话；除滑动过期外再设一个绝对上限（比如会员最长 30 天、后台最长 7 天必须重登）。
11. 登出时服务端让会话失效（版本号加 1 或删除服务端会话），响应带 `Clear-Site-Data: "cookies", "storage"`。

## 3. 注册

1. **必须在服务端核销短信验证码**（或等价的真人校验）。案例：旧官网注册提交不校验短信，被批量注册 65 个号；新官网同期被试了 1.6 万次，因为必须核销真实验证码，一个都没成功。
2. 所有注册入口共用同一套校验、同一个限速计数：官网、客户端内嵌页、微信扫码注册。旧入口要么升级，要么整站下线。
3. 用户名：
   - 拒绝控制字符（`\0`、`\t`）、所有空白、零宽和格式类字符（Unicode Format 类别）。数据库比较可能忽略 `\0` 和尾随空格，带这些字符的名字会和真实账号撞上，在后台里看着又一模一样。
   - 保留名检查（admin、管理员、客服、官方……）放在去除不可见字符之后；可再做 NFKC 规范化防全角、同形字冒充。
   - 长度和字符集白名单。
4. 推荐码、邀请码、来源码、支付宝账号这类附带字段同样做长度和字符集校验。攻击载荷里出现过 `' OR 1=1`、`../../x`、`%00`。
5. 贵的外部调用（IP 归属地、风控 API）放在限速和验证码核销之后。案例：每次注册在核销前先调两次外部归属地接口，1.6 万次注册变成 3 万多次第三方调用。
6. 新账号记录注册入口和版本，出事能分辨是哪个入口刷出来的。案例：只能靠"到期时间写成 2000-01-01"这个旧写法反推来源。
7. "登录名已存在"的提示无法避免枚举时，靠限速兜底；员工注册这类内部入口，考虑先核验短信再提示用户名冲突。

## 4. 找回密码、找回用户名

1. 必须短信或邮件验证码。
2. "用户不存在"和"手机号不匹配"返回同一句："用户名或手机号不正确"。
3. 同 IP 限速（10 分钟 10 次）。案例：攻击方两天打了 9.4 万次找回密码，用来试"用户名 + 手机号"组合。
4. 重置成功后让该账号所有旧会话失效（版本号加 1），不自动登录，并给账号绑定的手机或微信发一条"密码已修改"通知。
5. 用邮件链接重置时，链接里的域名从配置读取，不从请求的 Host 头拼（否则攻击者伪造 Host，用户收到的重置链接就指向攻击者的网站）；重置页加 `Referrer-Policy: no-referrer`。
6. 旧系统的找回口同样要关。案例：旧官网注册口关了，找回密码和发验证码口还开着——如果它不校验短信，知道用户名和手机号就能改别人密码，是最高优先级。

**人工渠道：客服代办**（正常档起）

攻击者冒充客户找客服，说"手机丢了，帮我换个号""帮我重置一下密码"，绕开所有技术校验，是最便宜的接管路径。

1. 原手机号还能收短信的，一律引导走自助流程，客服不代办。
2. 确实不能自助的，核对至少两项只有本人知道、且不在公开资料里的信息（最近一笔订单的金额、付款账户尾号、注册时间段）。身份证照片不能单独作为依据，泄露和伪造都很容易。
3. 客服只能发起，不能当场生效：走工单，留审计；有余额、有下级代理这类高价值账号由主管审批。
4. 生效后给原手机号和绑定的微信发通知，写明"如非本人操作请联系……"。
5. 改绑后设冷静期（如 72 小时），期间不能提现、不能改收款信息、不能导出数据。

## 5. 图形验证码

1. **不能让程序直接读出答案**：SVG 里不能有 `<text>` 明文，响应头和 JSON 里不能带答案或答案的哈希。案例：答案以 `<text>` 写在 SVG 里，对方程序直接读出，通过新官网发出了 111 条真实验证码短信。修复：字符改用字形轮廓 `<path>` 绘制。
2. 答案只存服务端，短有效期，校验一次即作废（对错都作废）。
3. 验证码和业务校验在同一个请求里完成。
4. **图形验证码只是减速带，不是防线。** 字形轮廓也能被程序识别：开源项目 svg-captcha-recognize 不做任何格式转换，直接按字形识别 svg-captcha 生成的验证码，作者实测 8.3 万次 100% 正确、每次不到 1 毫秒；开源 OCR（ddddocr）和打码平台能识别绝大多数位图验证码。挡住有收益的黑产要靠第 6 节的配额和熔断。
5. 验证码通过后，服务端签发一张**一次性凭证，绑定会话和这次要做的动作**（比如"给 138****0000 发短信"），发短信接口只认这张凭证。这样验证码的结果不能被重放，也不能拿去给别的号码发。
6. 高风险动作（发短信、失败多次后的登录）持续被刷时，升级为云厂商的行为验证码（滑块、点选），或工作量证明类验证码（ALTCHA、Cap 等开源项目：浏览器先算一道题，把单次请求成本从接近零抬到几百毫秒 CPU）。两者都只提高成本：工作量证明对廉价脚本洪水有效，对有收益的黑产不够；且低端手机解题慢。
7. 验收：自动测试断言输出里不含答案字符；线上取一张图看源码。

## 6. 短信验证码

1. 频控三重：同号（120 秒 1 条、每天 10 条）+ 同 IP（每小时 5 条、每天 20 条）+ **全站总量**（每小时 / 每天上限，超了熔断并告警；建议补）。另外设**每日短信费用上限**，到了自动停发并告警。
2. 业务只面向国内用户时，只给 +86 手机号发；国际号码会被用来做"短信费欺诈"（SMS pumping：攻击者和高价号码运营商分成，你付短信费）。
3. 网站的发短信接口会被黑产收录进"短信轰炸"工具（这类工具维护几百上千个网站的发码接口模板，可以反复调用）。能被做成模板反复调用的，都是不需要服务端一次性凭证、或验证码能被程序读出来的接口——所以第 5 节第 5 条的一次性凭证是关键。
4. 号码风险：虚商号段（162、165、167、170、171）和物联网卡号段（146）历史上是接码平台的主力。不要一刀切拒绝（正常用户也在用），对这些号段注册的新号加强校验、延迟发放奖励。云厂商有号码风险识别服务可选。
5. 验证码用安全随机数生成 6 位，10 分钟有效，一次性消费。消费用"条件更新"（`WHERE id=? AND 未使用`，看影响行数是否为 1），防止两个入口并发验证都通过。
6. 每个码最多尝试 10 次，各入口共用尝试次数，不能换个入口接着猜。
7. 确定没发出去（服务商明确拒绝）时撤回刚占的额度，否则用户重试时看到"120 秒内只能发一次"；调用异常时可能已送达，保留记录。
8. 发送场景区分：注册要求号码未注册，找回要求已注册。这本身会泄露号码是否注册，靠限速兜底。
9. 监控余额和日用量，异常告警。
10. 字段语义先核实再下结论。案例："IsSuccess"字段实际表示"验证码已被用掉"而不是"发送成功"，发送失败的记录会被删掉——一度据此误判"106 条全部发送失败"，并把错误结论转给了同事。

## 7. 密码存储与强度

1. 用自带盐的慢哈希：Argon2id、bcrypt，或 PBKDF2-SHA256（迭代次数按 OWASP 当年建议，2023 年为 60 万次）。哈希结果里带算法和参数版本，方便将来升级。
2. 老系统遗留明文 / MD5：在登录成功时透明升级为新哈希。如果是与其他程序共享的老表、改不动列，就在档案里记为已知风险，并限制能读这张表的数据库账号。
3. 密码规则：最少 8 位 + 常见弱口令黑名单；不强制"大小写数字符号"组合（用户会写在便签上）。
4. 管理员重置密码后强制首次登录改密，旧会话失效。

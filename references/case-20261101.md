# 教学案例：2026-11-01 攻击复盘

> 来自一个真实业务系统（文中称"参考项目"）的攻击处置交接包，只保留可复用的部分，已去掉项目名、手机号、账号等信息。

## 1. 背景

- 系统：对外官网 + 会员个人中心 + 员工 ERP 后台 + 代理后台，一个 .NET 后端，Windows Server + IIS，SQL Server。数据库与 PC 客户端、同事维护的旧系统共享读写。
- 攻击方：同一伙人，一台上海的服务器 + 四川南充的家用宽带，先后 3 个 IP。工具是 curl、python-requests、Python-urllib 和自制探测程序，伪装成浏览器 UA。

## 2. 时间线

| 时间 | 事件 |
|---|---|
| 10-22 全天 | 一个 IP 打了 5.2 万次：找回密码 3.1 万、会员注册 1.6 万、发短信 283 次（真发出 106 条）。**没人发现** |
| 11-01 11:46 | 主攻 IP 开始，3 小时 22.6 万次：代理后台登录爆破 14.3 万、找回密码 6.3 万、员工注册 8488、逐个扫后台接口 6000 多次 |
| 11-01 13:06 起 | 通过旧官网（同事服务器，注册不校验短信）批量注册垃圾号，再用这些号登录新官网，往发圈、服务单、客服反馈里塞 XSS，上传 SVG 脚本和名为 `../../web.config` 的文件，下 9999.99 元的待支付订单 |
| 11-01 下午 | 封 IP、删号（4 批共 65 个）、4 次紧急发版、装 IIS 动态 IP 限制 |

## 3. 结果

**守住的**：没有一次登录进员工后台或代理后台（后台数据接口 6000 多次全是 401 / 404）；新官网注册 1.6 万次一个没成功（必须核销真实短信验证码）；所有注入载荷被当作普通文字存储（全站参数化）；上传文件存储名由系统生成、云存储私有，没被执行；订单全部未付款。

**失守的**：图形验证码被程序读出，发出约 111 条真实短信；旧官网注册口不校验短信，产生 65 个垃圾号；攻击打了一整天无人察觉。

**守住的原因**：参数化写库、注册服务端核销验证码、后台陌生设备验证、Cookie 会话每请求校验、私有存储。这些都是开工时就布好的地基，不是事后补的。

## 4. 暴露出的漏洞与修法

| 漏洞 | 怎么被利用 | 修法 |
|---|---|---|
| 代理后台登录没接风控 | 14.3 万次爆破，只是没猜中 | 接入会员登录同一套失败风控 |
| 找回密码没限速、提示有两种 | 试"用户名 + 手机号"组合 | 同 IP 10 分钟 10 次；两种失败同一句提示 |
| 员工注册提示"登录名已存在" | 8488 次试员工登录名 | 同来源限速 |
| 验证码答案以 `<text>` 写在 SVG 里 | 程序直接读出，发出真短信 | 字形轮廓 `<path>`；发短信加同 IP 每小时 5、每天 20 |
| 9 个文件读 `X-Forwarded-For` | 限速、审计、员工常用 IP 可被伪造 | 全站统一只认连接地址 |
| 注册用户名没拦不可见字符 | `adm\0in2` 绕过保留名，`\0` 在数据库比较时被忽略，撞上真实账号 | 拒绝控制字符、空白、零宽字符 |
| 打包下载用客户上报的原始文件名 | `../../web.config` 进了员工下载的压缩包 | 只保留纯文件名 |
| 注册先调外部归属地再核验短信 | 放大成 3 万多次第三方调用 | 注册同 IP 10 分钟 10 次 |
| 旧官网仍在运行、注册不验短信 | 批量建垃圾号 | 同事关闭注册口；新系统在登录时拦截该特征的新号 |
| 没有全站频率兜底 | 单 IP 10 秒 1441 次 | IIS 动态 IP 限制 10 秒 300 次 |
| 没有告警 | 10-22 整天无人发现 | 需求已写（注册聚集、登录锁定发短信），待施工 |

## 5. 判断出错的地方（照实记录）

1. 垃圾号来源判断错两次：先说"客户端注册接口"，后查实是同事服务器上仍在运行的旧官网。
2. "106 条短信全部发送失败"是错的：把"验证码已被用掉"字段当成了"发送成功"。
3. 把"手机归属地为空"当成垃圾号特征，错了，正常号也是空的。
4. 一度想对所有"到期时间 2000-01-01"的号一刀切，会误伤 612 个付费客户。
5. 把 IIS 动态 IP 限制当成"超过就封"，实测是限速。
6. 说"找回密码的限速认伪造 IP"，错了：那处早已只认连接地址，真正认伪造 IP 的是另外 9 个文件。
7. 线上测不可见字符时一度以为新版本出错，实际是测试命令把 `\u0000` 变成了真实空字节。

共同原因：凭印象或字面意思下结论，没先查代码、没先跑数据。

## 5.5 攻击方画像（2026-11-02 对照开源工具调研后的推断）

- 日志里没有任何现成扫描工具的默认 UA（sqlmap、ffuf、gobuster 等都会自报身份），常用的 nuclei 默认随机 UA 也不会出现 `recon/1.0`。`recon/1.0`、`probe135`、`zz` 前缀、`xssprobe` 这些标记在公开工具、模板、字典里都搜不到。
- `python-requests/2.34.2` 是 2026-05 发布的最新版；`curl/7.88.1` 是 Debian 12 的默认版本，Python 官方 3.12 镜像正基于 Debian 12。推断（中等把握）：对方在一个新建的 Python 3.12 容器里跑自己写的脚本，不是一台装满现成工具的机器。
- 每类任务一个自定义 UA、测试数据自带可回收标记、载荷全是教科书最小样例（来自 PayloadsAllTheThings 一类资料）——像"让大模型现场写脚本"的风格（中低把握，也可能是人借助大模型写）。
- 可做成告警规则，但下次一定会变；根本还是按行为防。

## 6. 可复用的结论

1. 地基（参数化、服务端验证码、私有存储、后台二次验证）决定了"被打穿"还是"被打疼"。
2. 匿名接口逐个限速，比任何单点防护都有效。
3. 共享数据库的系统，安全水位由最弱的那个入口决定。旧系统要整站下线。
4. 发现比防护晚一天，损失就多一天。告警要和限速一起做。
5. 处置过程中的每个结论都要有证据，错了就更正。

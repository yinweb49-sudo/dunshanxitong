# 第 12 道盾：战时应急手册

## 0. 原则

- 先止血再查因；先保全证据再删除；先只读统计再请求授权；每一步做完回读核实。
- 对生产服务器的任何命令、对生产数据的任何修改，都要用户当次明确授权。授权只覆盖当时说定的那批对象：之后新冒出的账号、数据，要重新统计、重新问。
- 不动开发机本地网络。连不上生产服务器、第三方服务器时如实报告。
- 结论跟着证据走。前面说错了，在报告的"判断出错的地方"里照实更正。
- 和第三方（同事、供应商、云厂商）沟通的要求和更正，用可以直接转发的话写好。

## 1. 发现与定级（目标 15 分钟内）

**迹象**：请求量或带宽突增、短信余额骤降、注册量异常、登录失败日志刷屏、后台出现奇怪的用户名或内容、服务器 CPU 飙高、客户反馈收到莫名验证码。

**第一步：日志分诊**

```
python -I -X utf8 scripts/log_triage.py "<日志目录>/*.log" [--attack 已知IP] [--office 办公室出口IP]
```

输出回答：谁在打、每个 IP 多少次、打哪些接口、状态码分布、用什么工具（curl、python-requests 等）、几点开始、峰值多高、有没有扫敏感文件、有没有带外回连域名。再对照 `attack-defense-map.md` §9 的日志特征速查表，判断对方处在哪个阶段（侦察、扫描、利用、刷账号、刷业务）。

**定级**

| 级别 | 情形 | 响应 |
|---|---|---|
| P0 | 有成功登录后台、有数据被拿走、有资金损失、短信或计费资源正在被持续消耗 | 立即止血，同时通知负责人 |
| P1 | 正在爆破、刷注册、扫接口，但还没有得手 | 当天处置 |
| P2 | 零星扫描、探测敏感文件 | 记录，纳入下一轮加固 |

### 1.1 法定报告（定级时同时判断）

| 情形 | 依据 | 要做什么 |
|---|---|---|
| 个人信息发生或可能发生泄露、篡改、丢失 | 《个人信息保护法》第 57 条 | 立即补救，通知履行个人信息保护职责的部门和受影响的个人；采取措施能有效避免危害的，可以不通知个人，但要留存判断依据 |
| 较大及以上网络安全事件（大面积停服、大量数据泄露、造成较大经济损失等） | 《国家网络安全事件报告管理办法》（2025-11-01 施行） | 在规定时限内向属地网信部门报告（一般 4 小时内，关键信息基础设施 1 小时内；以办法原文为准） |
| 涉嫌违法犯罪（入侵、勒索、诈骗） | — | 是否报警由用户决定，证据按第 4 节保全 |

- AI 只给判断依据和报告要素草稿，报不报、怎么报由用户和公司负责人决定。
- 对接人（谁对网信、公安、客户）提前写进安防档案；事后补报比瞒报代价小得多。
- 只有扫描、爆破但没有得手、没有数据外泄，一般不触发上面两条，但判断过程要写进处置报告。

## 2. 止血（按见效快慢）

1. **封 IP**（手段见 `ip-ratelimit-blocking.md` §4）。先确认封禁手段真的生效：Windows 先看防火墙是否开启；封完回读名单，并看访问日志里该 IP 是否还有新请求。
2. **收紧限速**：临时调低全站频率阈值、调低被打接口的阈值。
3. **关闭被利用的入口**：旧系统、调试接口、已经不用的注册口。关完故意提交一条错误数据，看返回是不是已经 404。
4. **临时下线功能**：发短信、注册、上传。影响业务，先问用户。
5. **整站打不开、服务器负载却不高**：先去云控制台看这个 IP 是不是被拉进了黑洞（流量型攻击）。黑洞期间服务器上的限速、封禁全部无效，只能等解封或按档案里的预案切高防 / CDN（`server-hardening.md` §10）。切换涉及 DNS 和费用，由用户决定。

对方会换 IP（11-01 第一个 IP 被封后 15 分钟就换了第二个）。封 IP 只是救急，真正的防线是接口自身的校验和限速。

## 3. 损失评估（逐项给结论和证据）

| 问题 | 怎么查 |
|---|---|
| 有没有人登录进后台 | 攻击 IP 访问后台数据接口的状态码分布（全是 401 / 404 才算没进）；登录成功记录 |
| 有没有数据被拿走 | 敏感路径的 200 响应和响应大小；导出类接口的调用记录 |
| 有没有资金损失 | 攻击账号名下订单、余额、金币；支付回调记录 |
| 有没有产生费用 | 短信发送记录按秒对访问日志；AI、外部 API 调用量 |
| 写进来了什么 | 攻击账号名下每张表的数据；上传的文件 |
| 服务器有没有被拿下 | 网站目录完整性比对结果（新增或被改的文件）；新建账号、新服务、新计划任务、杀毒排除项（`server-hardening.md` §11） |
| 控制台有没有被动过 | 云操作审计：安全组、访问密钥、快照、DNS 的变更记录 |
| 注入有没有得逞 | 载荷是否被原样当文字存储（说明是参数化写入）；后台查看这些内容时会不会执行 |

**判断时的坑**

- 返回 200 不等于成功：很多接口失败也回 200，看响应体大小，或回业务库核对。
- IIS 日志时间是 UTC，北京时间加 8 小时。
- 字段先查语义再下结论（见 `auth-anti-abuse.md` §6 第 7 条）。
- 别只看自己的服务器：列出所有会写同一个数据库的系统。11-01 的垃圾号全部来自同事服务器上还在运行的旧官网，一开始误判成了"客户端注册接口"。

## 4. 证据保全

1. 拷访问日志，覆盖攻击全时段；当天的日志次日再拷一份完整的。生成 `SHA256SUMS.txt`。
2. 任何删除之前先导出 JSON 备份；上传的文件先留底再删。
3. 证据目录只放本机，不进 Git，不外传；报告里的手机号打码。
4. 嫌疑人（攻击 IP 和某个客户的上网地址重合）：导出该账号资料（不含密码）存证，账号是否处置、是否报警由用户决定。家用宽带地址会在同片区用户间轮换，重合不是铁证。

## 5. 清理攻击数据

1. 只读统计：攻击来源名下每张表各有多少行，列给用户。
2. 用户授权后，写计划文件，用 `scripts/purge_with_backup.ps1` 执行：先备份 → 行数与计划不一致就停 → 单事务删除 → 任何一步行数不对整体回滚 → 回读核实。
3. 识别特征要用数据证伪，防止误伤。案例：攻击号的特征是"到期时间 2000-01-01"，但这个特征下共有 1595 个号，其中 612 个付过费、93 个会员还有效——都是旧官网时期的老客户。最后收窄为"该特征 + 7 月 3 日以后注册"。
4. 被动防御：特征明确后，在"能不能登录"的统一判断里拦住这类账号，新冒出的号登录不了，不必上定时巡检。
5. 文件存储（本地目录、对象存储）里攻击号上传的文件，能归属的留底后删除；随机文件名、归属不到的，由用户决定追不追。

## 6. 根因修复

1. 按攻击面逐条列表：攻击方式 → 次数 → 结果 → 修复后的防护。
2. 每条修复带自动测试，按项目的发版流程上线，上线后在线上验证并记入发版台账。会真实产生费用或写生产数据的验证（真发短信、写审计）说明没做的原因，留到下次自然发生时顺手验证。
3. **横向排查同类问题**：一处读了转发头，全站搜；一个匿名接口没限速，全部列出来逐个看；一处打包没清洗文件名，搜所有打包和解压的地方。
4. 修复后回写项目安防档案。

## 7. 交接

1. 用 `templates/incident-report.md` 写处置报告，和证据、工具一起放成交接包，附"新对话开场提示词"，下一个人或下一个对话从这里接手。
2. 关键事实写进项目记忆：封禁怎么操作、攻击号特征、未完成的待办。
3. 给第三方的要求单独列清单，标优先级，附可以直接转发的话术；之前说错的，附更正话术。

## 8. 操作层面的坑（来自 11-01 处置）

**服务器与命令行**

- Windows 防火墙三个配置文件全关，加的防火墙规则不生效，改用 IPsec。
- `netsh` 输出是中文（936 编码），英文关键字筛不到；失败重试会重复添加筛选器。
- 远端是 Windows PowerShell 5.1：不认 `&&`，多条命令用 `;`。
- 从 Git Bash 调 PowerShell：`-Command "..."` 里的反引号会被 bash 吃掉，整个命令用单引号包。
- bash 的 `printf` 会把 `\\u0000` 变成真实空字节；要发"JSON 里写着 \u0000"的测试请求，用 `echo -n '{"name":"adm\u0000in2"}'`，先 `od -c` 看字节。
- Python 用 `-I` 隔离模式会忽略 `PYTHONIOENCODING`，中文输出报错，加 `-X utf8`。
- 开发机 DNS 走代理工具的假 IP，访问第三方服务器、核验旧系统接口要在生产服务器上做（经授权），不改开发机网络。

**数据库**

- 写 SQL 前先查列是否存在：生产库和文档、和测试库可能不一致。
- 数据库账号可能只能访问一个库，别的系统的日志在别的库、别的机器上，要向对方要。

**删除与授权**

- 安全闸拦下"删除新冒出的号"是正常的：之前的授权只针对当时那批。被拦的那条命令里如果同时改了脚本参数（比如期望行数），也会一起没执行，下次运行行数核对会失败——这是保护在起作用。

**发版**

- 应急期间极速发版也要用户原话授权；每次发版留旧版备份，记录版本号。
- 停应用池等待超时后强制结束进程，可能连带同机其他站点的进程，之后会自动恢复，要回头核实。
